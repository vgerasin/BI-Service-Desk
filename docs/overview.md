# О проекте

**BI Service Desk** — внутренний сервис команды BI / аналитики: единое место, где заказчики подают запросы
на дашборды и доработки, исполнители ведут работу и списывают время, а руководитель видит сроки, затраты и качество.

## Какую проблему решает

Запросы к BI-команде обычно живут в почте, мессенджерах и таблицах: теряются сроки, неясно, кто и сколько времени
потратил на какой отчёт, нет единого реестра дашбордов и источников данных, а оценить удовлетворённость заказчиков нечем.
Сервис собирает всё это в одну систему со сквозной цепочкой **заказчик → заявка → исполнитель → трудозатраты → отчёт → стоимость → оценка**.

## Для кого

| Роль | Что делает |
| --- | --- |
| **Заказчик** (портал) | Подаёт заявки, следит за статусом, отвечает на уточнения, оценивает результат |
| **Исполнитель** | Берёт заявки в работу, меняет статусы, списывает часы, ведёт реестр отчётов и источников |
| **Администратор** | Управляет пользователями, подрядчиками и справочниками, смотрит аналитику, формирует акты, настраивает интеграции |

## Ключевые идеи

- **Заявка — центр системы.** К ней привязаны заказчик, исполнитель, отчёт из реестра, юрлицо-плательщик, часы и оценка.
- **Честный SLA.** Время ожидания ответа заказчика в срок не засчитывается; просрочки и риски видны сразу в реестре и на дашборде.
- **Деньги считаются сами.** Ставки сотрудников и подрядчиков хранятся с историей, стоимость заявки и затраты по дашбордам
  вычисляются из трудозатрат; по ним формируются акты (DOCX).
- **Каталог данных рядом с заявками.** Реестр отчётов, источники данных, линейдж и база известных ошибок связаны с заявками.
- **Обратная связь встроена.** CSI-опрос из пяти вопросов приходит по ссылке без входа в систему.
- **Интеграции опциональны и настраиваются в интерфейсе.** SSO, SMTP, Telegram, справочник сотрудников и мониторинг обновления дашбордов
  включаются из раздела «Настройки»; секреты хранятся зашифрованными.

## Архитектура

```
 браузер ──► NestJS (REST /api, раздаёт собранный React) ──► PostgreSQL
                │                                              ▲
                ├── планировщик: эскалации, сводки, Telegram    │
                ├── SMTP / Telegram Bot API                    │
                ├── внешняя БД сотрудников (read-only, опц.)    │
                └── POST /api/dashboard-refresh-logs/ingest ◄── cron / n8n / скрипт (опц.)
```

- **Backend:** NestJS 10, TypeORM, JWT; модули: `requests`, `time-entries`, `ratings`, `acts`, `analytics`, `reports-ref`,
  `data-sources`, `known-errors`, `users`, `customers`, `contractors`, `employees`, `settings`, `notifications`,
  `escalation`, `telegram-bot`, `backup`, `activity-logs` и др.
- **Frontend:** React 18, Vite, Ant Design 5, TanStack Query; интерфейс на русском.
- **Хранилище:** PostgreSQL (схема синхронизируется TypeORM, отключается `DB_SYNCHRONIZE=false`) и том с вложениями.
- **Развёртывание:** один Docker-образ (API + статика) и PostgreSQL в `docker-compose.yml`.
- **Безопасность:** пароли — bcrypt, секреты интеграций — AES-256-GCM (ключ из `JWT_SECRET`), секреты не возвращаются в браузер,
  порт БД наружу не публикуется, закрытые для анонимов маршруты защищены JWT.

## Основные сущности

`requests` (заявки и их статусы) · `time_entries` (трудозатраты) · `users` / `contractors` / `customers` · `rate_history` (ставки) ·
`reports_ref` и `report_versions` (реестр отчётов) · `data_sources` · `known_errors` · `request_ratings` (CSI) ·
`billing_companies` (юрлица для актов) · `activity_logs` · `settings` (настройки и зашифрованные секреты).

## Ограничения и планы

- Интерфейс только на русском (строки не вынесены в i18n).
- Нет встроенного e-mail-ввода заявок: заявки создаются в интерфейсе и портале.
- Схема БД ведётся через `synchronize`; для строгого контроля миграций отключите его и ведите миграции самостоятельно.
